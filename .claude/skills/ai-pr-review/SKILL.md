# AI PR Review

Automated audit of code changes before opening a Pull Request. The skill analyzes the diff, checks compliance with the CyberArk and Spring Boot conventions used in this repo (`conjur-spring-boot-sdk`), and generates a report ready to paste into the PR description.

## Workflow

### 1. Context Extraction

- Run `git diff` against the base branch (usually `master`).
- Identify the changed components by package (see `CLAUDE.md` for the full layout):
  - `annotations/` — public API (`@ConjurPropertySource(s)`, `@ConjurValue(s)`, `Registrar`)
  - `core/env/` — `ConjurConfig`, `ConjurConnectionManager`, `AccessTokenProvider`, `ConjurPropertySource`
  - `processor/` — `SpringBootConjurAutoConfiguration`, `ConjurCloudProcessor`, `ConjurValueClassProcessor`, `ConjurRetrieveSecretService`
  - `service/` — property-source/processor chain implementations
  - `util/` — `ConjurResilientAuthenticator`, resilience4j registry/config, `ConjurSecretUtils`
  - `domain/` — `ConjurProperties` (bindable `conjur.*` config)
  - `SpringBootExample/` — sample app / integration-test harness

### 2. Multi-Persona Analysis

- **Architect**:
  - Autoconfiguration classes must be registered in *both* `META-INF/spring.factories` (Spring Boot 2.x mechanism) and `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` (Spring Boot 3.x mechanism) — flag any new/renamed `@Configuration`/autoconfig class that only updates one of the two.
  - New property-source/processor logic should go through the existing chain abstractions (`PropertyProcessorChain`, `DefaultPropertySourceChain`, `CustomPropertySourceChain`) rather than bypassing them.
  - Retry/resilience behavior should stay opt-in via `conjur.resilience-enabled`, consistent with `ConjurResilientAuthenticator`.
- **Security**:
  - No hardcoded Conjur secrets, API keys, certs, or `.pem`/`api_key` files committed (these are test-only artifacts generated by `SpringBootExample/start`/`stop` and must stay gitignored).
  - Apply the DisCo-style secret-scanning checklist from `docs/secret-scanning-guide.md`: for any new secret-injection path (annotation, `@Value`, property source), verify a resolved secret value is never logged, serialized, or exposed in an exception message/toString.
  - Validate `conjur.account`/tenant-equivalent config is present and checked before use, not silently defaulted.
- **Quality**:
  - New/changed functionality in `src/main/java` must have corresponding JUnit 5 tests under `src/test/java` mirroring the same package, with meaningful JaCoCo coverage.
  - If the change affects end-to-end behavior (auth flow, property resolution), check whether `SpringBootExample` integration tests (`start`/`start_enterprise`) need updating too.

### 3. Standard Compliance

- Java baseline is 17; Spring Boot baseline is the 3.x line (`spring-boot-starter-parent`) — flag any dependency or code that requires a newer/older major without justification.
- Do not hand-edit the `<version>` in `pom.xml` — it's overwritten by `build-package.sh` from `CHANGELOG.md`; flag PRs that bump it manually.
- No use of deprecated/blocked APIs inconsistent with the existing `conjur-sdk-java` (4.2.2) client contract.
- `run-tests.sh` is currently a stub; don't rely on it as the source of truth for "tests pass" — actual unit tests run via `mvn test`.

### 4. Report Generation

Generate a `PR_REVIEW_REPORT.md` file containing:

- ✅ Summary of changes
- ⚠️ Critical remarks (Blockers)
- 💡 Optimization suggestions
- 🧪 Test status

## Usage Instructions

Run this command before every commit that finalizes a task:

```
@ai-pr-review run analysis and generate report
```
